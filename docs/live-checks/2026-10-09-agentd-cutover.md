# 2026-10-09: does an account's control agent answer on the Python implementation?

**Why.** ADR-040 Wave 8, step s7: the cutover of the control agent from `runtime/control/agentd.mjs` to `tools/fabric/control/agentd.py`. The parity suite shows byte-equal replies, so the wire cannot show the switch; the account's unit is where it is read. `runtime/control/agentd.json` selects the implementation per login: default `node`, and the coordinator's own account first under `python`. Bootstrap writes the unit's ExecStart from it, and a changed unit is reloaded and restarted. Then the rest of the fleet, one login at a time, and last the default.

**Measured on the first account, `user`, 2026-10-09:**
- The unit. `grep ^ExecStart ~/.config/systemd/user/agent-fabric-agentd.service` shows `ExecStart=/usr/local/bin/fabric-python %h/projects/agent-fabric/tools/fabric/control/agentd.py`. The Node line was `ExecStart=/usr/bin/env node %h/projects/agent-fabric/runtime/control/agentd.mjs`. Measured: `ExecStart=/usr/local/bin/fabric-python %h/projects/agent-fabric/tools/fabric/control/agentd.py` on `user`, 2026-10-09 21:24 UTC.
- How it got there: bootstrap by hand (moveto), or `fabric-ctl <login> upgrade fabric`, where bootstrap leaves the restart to the daemon and the daemon exits after its reply. The bootstrap line `* agent-fabric-agentd.service runs python (runtime/control/agentd.json)`. Measured: bootstrap by hand. `fabric-ctl all upgrade fabric` after #154 got no answer from `user` (its own agentd restarting) and the unit stayed Node; `fabric-status` said `DRIFT: the unit runs node, runtime/control/agentd.json selects python`, and `bash runtime/claude-code/bootstrap.sh` printed `* agent-fabric-agentd.service runs python (runtime/control/agentd.json)` and wrote the unit.
- The process. `systemctl --user status agent-fabric-agentd` shows `active (running)`, its main PID running `/usr/local/bin/fabric-python …/agentd.py`, and no restart loop in `journalctl --user -u agent-fabric-agentd`. Measured: `active`, MainPID 971791 running `/usr/local/bin/fabric-python /home/user/projects/agent-fabric/tools/fabric/control/agentd.py`, NRestarts=0.
- The account's own read-back. `fabric-status` shows the line `agentd       python (the unit's ExecStart, as runtime/control/agentd.json selects)`, and no DRIFT. Measured: `agentd       python (the unit's ExecStart, as runtime/control/agentd.json selects)`, no DRIFT.
- The wire. `fabric-ctl <login> status` answers, and its `agentd` block (`pid`, `started`, `uptime_s`) names the Python process's pid and a start after the switch. The reply carries no implementation field; the wire is frozen, so the pid is how the two are matched. Measured: `fabric-ctl user status` answered `ok` (fabric eec45fdc); its `agentd` block is `{"pid": 971791, "started": "2026-10-09T21:24:53.119Z", "uptime_s": 129}`: the Python process, started at the switch.
- One fleet round trip. `fabric-ctl all jobs` answers from this account, on Python, and from every Node account in the same call. Measured: `fabric-ctl all jobs` returned every account's rows in one call, `user` on Python and the rest on Node.

**Not measured here.** The rest of the fleet: each login added to `python` gets its own read-back in this file. The default goes to `python` only once every placed login has answered on it.

**What it decides.** Whether the next logins move to `python`. If a read-back fails, the login comes off the list, and the next bootstrap puts the Node unit back.

**2026-10-10: the default moves before the per-login rounds.** The owner chose to switch the whole fleet at once ("yes, switch the fleet to python agentd"), after one account had run on Python for a day with no restart and no drift. So the gate above, every placed login answering first, was not the one applied: the default goes to `python` in #166 and the per-login list empties. The fleet read-back goes here after the distribution: each account's `fabric-status` agentd line and its `fabric-ctl <login> status` agentd block (pid and start after the round), with any login that does not answer named. The way back for the fleet is the default set to `node` and a distribution; the selector has no per-login `node` list, so one failing account is recovered by that, or by a `node` list added then.
