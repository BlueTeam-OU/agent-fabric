# ADR-043 — amendments

The full notes; the ADR's body reads current and its Amendments table lists them.

### Amendment 2026-10-09 — A mod or MCP server that runs code passes the fleet's guards

The owner asked for an analysis of a context-saving MCP server (2026-10-09). It runs code in a dozen languages for the session and returns only the output, and its hooks route the session's shell calls to it. The read of its source found that each run is a child process with the session's environment, files and network, so a shell command run through it reaches none of the fleet's `PreToolUse` guards, which see only the harness's own tools. Rule 5 already made every mod a reviewed proposal; rule 8 says what that review refuses: an execution path that bypasses the guards, and a process boundary presented as isolation. No mod of the fleet runs code today.

### Amendment 2026-10-09 — Rule 8 names its gate: the managed MCP allowlist

The blind review of the merged rule 8 (#130's last commits) found that it refused a code-running MCP server "at review" while no rule sent an MCP server to review: rule 5 covers mods, and a login's or a project's own MCP configuration reaches a session unreviewed. gzapp's `.mcp.json` already starts `dart mcp-server`, a Flutter toolkit script and `npx -y @playwright/mcp@latest`, unpinned. Claude Code 2.1.285, the fleet's pin, has managed `allowManagedMcpServersOnly`, `allowedMcpServers` and `deniedMcpServers` (read from the installed build), so the gate is rule 1's file. The review also found the reason too broad: an unmatched `PreToolUse` hook does see an MCP call; what an MCP call escapes are the guards matched to Bash, and what no hook sees is the server's own processes. Both are now said.

### Amendment 2026-10-31 — Rules 1–2 built: exec-form guards through one root-owned entry, a snapshot of a named main, `fabric-managed`

The owner chose, on 2026-10-31, to put rules 1 and 2 in force before the pin moves (option 1), rather than amend rule 6. The live read-back on 2.1.316 (`docs/live-checks/2026-10-31-managed-settings-2-1-316.md`) settled three things the original rule 2 left open. A managed hook inherits the session's `PATH` and environment, so a root-owned script is not enough: what it execs by name, and the fabric root it reads, would still be the login's. The guards therefore run through one root-owned entry. Its hook is exec form, so no shell parses it; it clears the environment and names its own root and interpreter. Second, the guards import modules and read routing and policy data, so the root-owned copy is a snapshot of the whole tree they read, of one sha the operator names. It is extracted by git plumbing, because `git archive` and a checkout apply filters from the login-writable repository config, which would run as root. Third, the review class lost its Bash fence hook when ADR-065 took Bash from it, so the managed review fence denies by `agent_type` instead. Rule 9 records the owner's answer of the same day: every guard change needs the operator's reinstall on each host. It also records the Qubes AppVM boot restore, since there `/etc` is rebuilt at boot and `/usr/local` is kept, and the check `fabric-ctl all status` runs. During the transition, each workspace copy of a guard stands down only where the installed managed file names that guard, so a host is never without one: a file installed from an older main leaves a guard added since running from the workspace (the blind review of #451 found the first gate, the file's mere presence, left such a guard running nowhere).

### Amendment 2026-11-03 — The session seal is a managed hook

Designing rules 1–2 (job j509) found one more hook a login could drop by editing its own settings: the SessionStart step that unsets the session's secrets in the file the harness sources into every Bash call (ADR-038 rule 9). It lived inside `session-start.py`, the start-context hook, which rule 2 leaves in the workspace because it only informs. It is now its own program, `runtime/claude-code/hooks/session-seal.py`, named in `hook_entry.py`'s table and in the template's `SessionStart` event, and run exec'd as the plan hold is, because it never refuses. Its workspace copy is a call from `session-start.py`, not a settings entry of its own: a launcher pull updates the fabric's code but not a login's rendered settings, which change only at the next bootstrap, so a new entry would be missing wherever an account pulled without bootstrapping (the blind review of #464 found the first version, a separate entry, leaving such a session with no seal at all). Unlike the guards, its workspace copy does not stand down where the installed file names it. The harness gives each `SessionStart` hook its own env file, so the two copies write one line each, and an unset run twice does nothing. The 2.1.316 read-back covered `PreToolUse` hooks only. A second read-back the same day (`docs/live-checks/2026-11-03-managed-sessionstart-env-file.md`) found that a managed `SessionStart` hook receives `CLAUDE_ENV_FILE` and its unset reaches Bash, on 2.1.286 and 2.1.316, whatever the login's `disableAllHooks` says. The workspace copy still never stands down: it costs one line, and it is the only seal on a host whose installed file predates it.

### Amendment 2026-11-03 — Rule 6 met: the pin moves to 2.1.311

The owner moved the fleet to Claude Code's npm stable on 2026-11-03 (job j560). The target was 2.1.311, because the `stable` tag had moved there from 2.1.309. Rule 6 allowed the move once `fabric-ctl all` reported rules 1 and 2 in force on every host. It reported `managed in force` for all 30 accounts on develop-qzapp, the registry's only host, and `fabric-managed probe` passed on 2.1.311: a class dispatch with no model is denied, and `--plugin-dir` is refused. Before the pin moved, the claims the fleet had read only on other builds (2.1.274, 2.1.286, and for the managed hooks 2.1.316) were read back on 2.1.311: the managed exec-form hooks, a hook that cannot spawn, the worktree import approval, what `--system-prompt-file` replaces, the subagent transcript, and the dispatch guard's second run under `run_in_background`. Each held, the two hooks that cannot run at project scope only (`docs/live-checks/2026-11-03-claude-code-2-1-311-readback.md`). The merge of the pin itself drifts the host's snapshot, so the operator reinstalls before `fabric-ctl all upgrade claude`, which refuses until then. The two cases of a hook that cannot run were measured at project scope this time, not under `/etc`, and gave 2.1.316's results: a missing script blocks the call, and a missing interpreter lets it run. A managed guard whose interpreter is missing is therefore still off, which is why `fabric-managed check` reports a missing interpreter. Rule 6 itself is unchanged, and a later pin move is reviewed like any other change.

### Amendment 2026-11-10 — The pin moves to 2.1.322, npm's `latest`

On 2026-11-10 the owner moved the fleet off npm's `stable` tag, which the 2026-11-03 move had followed, to `latest` (job j749). That day `stable` was still 2.1.311 and `latest` was 2.1.322. The owner first named 2.1.321, which the owner took to be the first build that knows `claude-fable-5-2`, and chose 2.1.322 when asked. Two reasons: 2.1.311 does not know Fable 5.2 (it prints `unrecognized_model` for it, measured), and a vendor post of 2026-11-04 says builds from 2.1.316 make a background subagent's progress summaries much cheaper (said, not measured). Before the pin moved, the 2.1.311 read-back's claims were read again on 2.1.322 (`docs/live-checks/2026-11-10-claude-code-2-1-322-readback.md`), and each held. Two things moved, and neither changes what the fleet does. The agent listing now arrives in a system message instead of the Agent tool's schema, outside the text a replacement prompt replaces, as before. `run_in_background` no longer runs the managed Agent hook a second time, so the dispatch guard's acceptance of its own answer stays only for accounts still on an older build. The build also reads `CLAUDE_CODE_SUBAGENT_EFFORT`, which ADR-006 rule 6 now fences. Rules 1 and 2 were installed on every host, from a snapshot older than main, so `fabric-ctl all status` read `managed drifted` on all 30 accounts, not `in force`. Rule 6 as written covered every move to 2.1.287 or later. Its purpose was the first crossing, which it gated on 2026-11-03, and the 2026-11-03 note already said a later move is reviewed like any other change. The blind review of this change found the rule did not say so (#549). Rule 6 now says it: after the first crossing, the gate is each install. `fabric-ctl <login> upgrade claude` already refused a build at or above 2.1.287 while the host's managed settings were not in force. `new-agent` installed the pin with no such check, which the second blind review of #549 found. It now asks the same check, `upgrade.managed_refusal`, and holds `stable` and `latest` as builds past the floor, since they name no version. Those are the fabric's only two ways to install Claude Code, so no account it installs runs 2.1.322 before the operator reinstalls. The order after the merge stays: the operator's reinstall (rule 9), then `fabric-ctl all upgrade fabric`, then `fabric-ctl all upgrade claude`. `latest` is the owner's choice for this move, not a rule: the next one names its build as this one did.
