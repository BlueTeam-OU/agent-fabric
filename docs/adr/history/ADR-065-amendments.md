# ADR-065 — amendments

The full notes; the ADR's body reads current and its Amendments table lists them.

### Amendment 2026-10-31 — A full review carries the findings earlier chains left open

#425 merged with F5 open. An earlier review chain raised it, nothing judged it, and a fresh full review of the head started a chain of its own, which the review gate read as "head reviewed". Gate 4c of `fabric-pr arm` now refuses on a finding open in any chain (`tools/fabric/github/arm_findings.py`, #437). That closes the merge, but the next full review still did not know the finding existed, so the PR could only be armed by a re-review on the old chain or a `--defer`.

A PR's full-review brief now reads the PR's reviews with the same reader and from the same accounts (the PR's author and `AGENT_FABRIC_REVIEW_POSTERS`), and lists each open finding with its label, level, place and the head it was raised on, for the reviewer to answer in a `Judgement:` line. The reviewer numbers its own findings past every label the PR's reviews used, closed ones included. A judgement goes to its own chain whenever that chain raised the label, so a new F5 would take the judgement meant for the old one. A finding raised on the head under review is another engine's same round, and blind review (ADR-020) keeps it out; its label still counts. Reviews that cannot be listed refuse the render, and so does a listed review that cannot be read (no body, no machine lines, a malformed line), since rendering either as none is the gap this closes: its open findings would go uncarried and its labels reused (#437 round 3, F6). The Codex engine is handed none: its answer carries findings only and its renderer numbers them from F1, which a follow-up of its own changes.

### Amendment 2026-11-01 — A coverage block may carry a default entry

A memory drain's range is a thousand paths, and a block naming each one was 148KB against the 60000 characters a block may hold, so its review could not be posted at all (#447). A block may now carry an optional top-level `"default": {"status", "reason"}`, the entry of every path of the range the block does not name. It is a key of its own, not a path called `*`, since a file may be called that. A path the block names keeps its own entry whatever the default says, and a path named outside the range is still refused, so the default never widens what a review may claim. A `not read` default makes the review partial, and the line after the marker says so: the block alone cannot show that no path falls under it, so it is never counted as coverage of the head. A block without a default reads and posts as before. The Codex engine builds its block from its answer schema's per-path arrays and does not yet emit a default.

### Amendment 2026-11-04 — A moved report's re-review reads its machine lines

A report that with its block is over the 65000 characters a review holds is posted as a PR comment first, and the review keeps the marker, the partial line, the report's `Finding:` and `Judgement:` lines, the block and the comment's link (#370). §2 C said the previous report is the checkpoint review's posted body, which for such a review is not the report: the re-review brief quotes the body (`review_checkpoint.last_checkpoint_review`, `review_brief`), so the reviewer is handed each finding's label, level, place and summary, and not its prose. A memory of the coordinator's had read the gap as needing `previous_findings` typed as a file, which §5 rule 5 refuses on a PR's re-review (python-dev-03's REPLY 01a16fcd-3881 raised the question).

The body stays the previous report, and the rule now says what it holds. The brief does not follow the link: the comment is a second object no marker names and no check ties to `post-review`, while the body's machine lines are exactly what `fabric-errors` and gate 4c of `fabric-pr arm` read, so the re-review judges the same findings the gate counts. The reviewer reads the tree for each finding's place, and a finding whose line is too thin to judge is answered `partly` with what it could not see, which the gate keeps open. Fetching the comment would also bring back the size the move was made to avoid into a brief that already carries the re-review diff. No code changes.

### Amendment 2026-11-13 — An adjudication closes a finding from any earlier round

gzapp#1246 could not be armed. A finding raised in round 1 of a three-round review stayed open in gate 4c: the only review that could judge it was one based on round 1's head, and that base is neither the PR's merge-base nor its last checkpoint's head, so `post-review` refused to post it. A judgement in a later round went to that round's own chain, and the old finding was not in it. The owner chose `--defer` on 2026-11-12, and the gap was contracted to devex-tooling (REQUEST 01a1cf77).

`post-review` now accepts one more base: the head of an earlier posted review of the PR that raised findings, for a report whose machine lines are only `Judgement:`s of labels raised on that head and `Finding: none`, read at a later commit. It writes `review_coverage.ADJUDICATION_LINE` as the body's second line. Gate 4c (`arm_findings`) applies such a review's judgements to the findings raised on its base and to no other, which tells apart two rounds that both number an F1. One that raises a finding is read as unknown, since no later review would judge its findings. An adjudication is no link of any chain and is never a checkpoint (`review_checkpoint` sets it aside); taken as one, it would move the next review's base back to the head it adjudicated. Nor is it a review of its head at gates 4 and 4b (`review_status.verdicts.uncounted_v2` names it): its reviewer may raise no finding, so counted there it would cover commits after its base that nobody reviewed. For the same reason the brief refuses a base that is the last checkpoint's head, where `post-review` would take the report as the next round. The brief's `finding-adjudication` mode, which had refused every range but head..head (j558), renders base..head for a PR when its base raised findings, and lists them from the posted reviews.
